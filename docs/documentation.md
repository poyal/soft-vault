## 채택하지 않은 부분

- Android APK·서명 키·versionCode·에뮬레이터·SAF와 Electron/Qt/NSIS 전용 명령은 가져오지 않았다.
- 다른 프로젝트의 실사이트 검사·2시간 부하·원격 게시 예외·필수 승인 절차를 Soft Vault의 기존 요구로 해석하지 않는다.
- 다른 프로젝트의 자동 manifest·게시 잠금·설치본 전체 E2E가 Soft Vault에도 있다고 쓰지 않는다. 실제로 추가한 소스 지문·Mac 설치 검사 도구는 해당 파일과 검증 기록으로 확인한다.
- 일부 프로젝트의 종료 즉시 모든 중간 자료 삭제 규칙은 그대로 적용하지 않는다. 현재 Soft Vault는 로컬 패키지를 직접 사용하며 공개 재다운로드 보장이 없다. 유일한 검증 파일·복구 근거·실행 중인 앱을 먼저 보존한다.
- 릴리즈 결과를 `AGENTS.md`에 저장하는 관례는 따르지 않는다. Soft Vault에서는 결과를 `VERIFICATION.md` 또는 날짜별 검증 문서로 구분해 실행 지시와 혼동하지 않는다.

## 문서별 책임

루트 README는 소개·설치·기본 사용과 문서 입구다. 계획서는 요구사항·사용자 결정·범위를 유지한다. `docs/`의 공통 가이드는 운영 절차를 한 번만 정의하고, 검증 문서는 당시의 기기·소스·파일·실제 결과만 기록한다.

배포 버전 기록은 `docs/releases/v<버전>/README.md`에 사용자 안내, `VERIFICATION.md`에 최종 검증을 둔다. [0.1.0 기록](releases/v0.1.0/README.md)은 두 OS 검사와 설치 사본 확인 결과를 바탕으로 작성했다. 검증되지 않은 개발 결과는 `docs/verification/`에 두고 배포 완료로 표현하지 않는다. 릴리즈 노트 템플릿은 게시 본문 작성용이며 같은 패치 노트를 여러 파일에 반복 보관하지 않는다.

## 작성·갱신 기준

1. 기능 안내는 진입 위치 → 입력/선택 → 버튼 → 결과 순서로 쓴다. 실제 메뉴 이름을 확인하고 미구현 버튼을 안내하지 않는다.
2. 앱 기능 변경에는 해당 사용자 안내·시나리오·필요한 캡처를 갱신한다. 문서에 포함되는 코드나 번들 도움말 변경은 단순 문장 수정과 구분한다.
3. 표에는 구현 상태와 검증 상태를 따로 적는다. 검사 수·백분위수·코덱 수·화면 수의 단위를 구분한다.
4. 캡처에는 소스·빌드 모드·기기·크기·합성 데이터·실제/시안 여부를 남긴다. 파일 이름만 보고 최신 화면으로 판단하지 않는다.
5. 각 기록에는 날짜·명령·로그·해시·미검증 범위가 있어야 한다. 후속 문서 수정이 기존 바이너리를 다시 검증한 것처럼 시각을 바꾸지 않는다.
6. 문서 수정 뒤 상대 링크·로컬 파일·명령 이름·버전·표의 합계를 확인한다. 문서만 바뀌었다면 앱 빌드·E2E는 반복하지 않는다.

현재 `build/` 보고서는 생성물이고 Git에 없다. 공통 문서의 절차와 장기 요약은 저장소만으로 읽히게 유지하고, 원시 결과 링크는 로컬 근거임을 표시한다. 배포 ZIP에 현재 docs 전체를 포함하는 자동화는 없으므로 오프라인 매뉴얼이 번들된다고 안내하지 않는다.
