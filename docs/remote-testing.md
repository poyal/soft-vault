# Mac·Windows 원격 실기 검증

이 문서는 연결과 향후 검사 절차를 정리한다. SSH 인증 성공, 로그인된 데스크톱 존재, 앱 테스트 통과를 구분한다. 아래 환경은 2026-11-08에 확인한 값이다.

## 연결 정보의 관리

실제 IP·사용자명·키는 사용자 전역 `~/.ssh/config`에서 관리하며 이 저장소에 복제하지 않는다. 현재 별칭은 다음과 같다.

```text
ssh mac-mini-m4
ssh windows-test
```

두 별칭 모두 공개키 인증을 확인했다. 개인키는 로컬에 보관하고 대상에는 공개키만 등록한다. 새 PC에서는 같은 별칭을 해당 환경의 전역 설정에 준비해야 한다. 이 문서만 복사한다고 인증 설정까지 복원되지 않는다.

| 환경 | 확인한 내용 | 아직 확인하지 않은 것 |
| --- | --- | --- |
| 기존 Windows 개발 PC | i7-8700B, UHD 630, RAM 63.8GiB; 기존 앱 검사 근거 있음 | 깨끗한 OS 신규 환경, 실제 HDR 출력 |
| Mac mini M4 | arm64, macOS 27.0.1/26A434, SSH·로그인 데스크톱 계정 확인 | 앱 빌드·UI·패키지·코덱·성능 |
| 별도 Windows | Windows 11 Pro/26300, Ryzen 7 9700X, RTX 4070 Ti, RAM 31.7GiB, V32UE·ASUS MB16AC | 앱 설치·E2E·HDR 활성화/출력·성능 |

최초 조회 때 Mac은 Command Line Tools를 선택하고 있었고 Xcode 다운로드가 진행 중이었다. 이후 사용자가 Xcode 27.2와 초기 설정, CocoaPods 1.17.0 설치를 완료했다. 양쪽 격리 작업 폴더에 Flutter 3.47.9를 준비했다. Windows는 VS 2022 BuildTools를 사용한다. PATH 조회 실패를 기기 전체에 도구가 없다는 증거로 삼지 않는다.

## 실행 준비

1. 대상 별칭·OS·아키텍처와 원격 작업 폴더를 확인한다. 사용자 작업 폴더·개인 라이브러리를 시험 경로로 쓰지 않는다.
2. 같은 소스 기준과 `pubspec.lock`을 전달한다. 미커밋·미추적 파일이 있으면 단순 HEAD 복제로 현재 구현이 전달되지 않으므로 파일 목록·소스 지문을 따로 고정한다.
3. `.git`, 개인 데이터, `.ssh`, 토큰, 다른 OS의 `build`·`.dart_tool`·네이티브 DLL을 무차별 복사하지 않는다. 합성 fixture는 해시를 기록해 전달한다.
4. 도구 버전과 필요한 네이티브 런타임을 해당 OS에서 준비한다. Mac의 `MediaTools.bundledBin()` 경로와 FFmpeg·ffprobe 배치를 실제 `.app` 구조에 맞춰 검증해야 한다.
5. SSH의 비대화형 세션과 실제 로그인 데스크톱에서 실행되는 테스트를 구분한다. SSH로 프로세스를 시작했다고 화면 입력·표시까지 확인한 것으로 기록하지 않는다.
6. 결과를 새 실행 ID로 수집하고 소스·기기·모드·명령·해시를 함께 가져온다. 원격 프로세스는 시험에서 생성한 PID·경로만 종료한다.

Windows 스크립트는 PowerShell, Mac의 `verify-macos.sh`·`package-macos.sh`·`verify-install-macos.sh`는 bash 실행 기준이다. Windows 코드·테스트가 Mac에서 그대로 통과한다고 가정하지 않는다. Mac sandbox는 entitlements에서 꺼져 있다. 임시 GUI 작업 등록과 절전 방지는 종료·실패·시간 초과 시 해제하고, 재로그인 때 자동으로 검사가 다시 시작되는 설정을 남기지 않는다.

PowerShell에서 원격 스크립트를 전달할 때 따옴표·문자 인코딩·CRLF 차이를 확인한다. Windows 대상 PowerShell은 적절한 인코딩의 `-EncodedCommand`, Mac 대상 셸은 LF 스크립트 파일 등 재현 가능한 전달 방식을 사용한다. Base64는 전송 인코딩이지 비밀 보관 수단이 아니다.

## HDR 검증의 단계

| 단계 | 확인할 것 | 판정 |
| --- | --- | --- |
| 소스 자료 | HEVC 10bit·색 원색·전달 함수·메타데이터·파일 해시 | HDR 입력 자료 조건 |
| 디코딩 | 실제 프레임·해상도·탐색·드롭/오류·음량 | 디코더 동작 |
| OS 출력 경로 | HDR 지원/활성화, 연결 포트·케이블·활성 모니터·주사율·렌더러 | 실제 출력 준비 |
| 실물 화면 | SDR/HDR 전환, 클리핑·검정·밝은 영역·색·자막·전체화면 | 직접 관찰 결과, 측색 여부 별도 |
| 지속 재생 | 정한 재생 시간·전환·CPU/GPU·메모리·프레임 | 해당 부하 조건의 안정성 |

현재 4K HDR fixture 디코딩 통과는 OS HDR 출력·색 정확도 통과가 아니다. 원격 화면·일반 PNG는 물리 화면의 밝기·색을 그대로 증명하지 않는다. DisplayLink와 GPU 직접 연결의 경로도 구분해 기록한다. 실제 출력이 지원되지 않거나 SDR로 변환되면 그 사실을 결과에 남긴다.

## 종료와 다음 단계

테스트가 바꾼 창·HDR·음량·임시 서비스·시험 경로의 원복 여부를 기록한다. 사용자 앱·전역 SSH 설정·개인 자료는 유지한다. Mac 빌드·번들링 → 플랫폼별 기능·설치 사본 → 데이터 보존 → 성능·HDR 실기 순서로 준비하되 실제 실행 결과만 [검증 템플릿](templates/verification.md)에 반영한다.
