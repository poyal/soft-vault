# 영상 재생 품질 검증 — 2026-11-15

2026-11-15~16에 Windows와 Mac에서 같은 자료로 측정했다. 릴리즈 빌드·패키징은 사용자가 다른 장비에서 수행하므로 이번 작업에 포함하지 않는다.

## 문제와 수정

기준 소스는 `7108c288c744163c706931c87871dd94fab12723`이다. 원본 소스의 profile 앱과 같은 측정 코드를 사용하는 수정 앱을 비교한다. 테스트·진단 파일만 기준 사본에 추가하며 기준의 제품 코드는 수정하지 않는다.

기준 앱은 각 키 입력을 디코더의 지연된 현재 위치에 더했다. 실제 10초 위치에서 +5초 입력 10회를 보내도 60초에 도달하지 않았다. 슬라이더는 모든 이동 이벤트에서 정밀 탐색을 요청했다. 입력 목표를 별도로 누적하고, 최신 목적지만 남기고, 드래그 미리보기는 150ms 간격의 키프레임 탐색, 놓는 순간은 정밀 탐색으로 바꾼다. ±1초 조작은 정밀 탐색을 유지한다.

번들 mpv 0.36의 `seek` 명령은 연속 탐색에 최대 300ms의 대기를 적용한다. 최종 정밀 이동은 이 대기 플래그가 없는 `time-pos` setter와 `hr-seek=yes`로 실행한다. EOF에서 다시 이동할 때는 media_kit의 완료 상태도 초기화한다. 파일 교체 시에는 이전 요청을 비우고 새 파일이 준비될 때까지 입력을 막는다. 배속 재생 중 이동 직후 일시정지하거나 배속을 낮추더라도 이미 재생된 시간을 완료 판단에 반영한다.

재생 중 자동 스캔·메타데이터·썸네일 작업은 중단/연기하고 일시정지 후 재개한다. 중단된 스캔은 아직 방문하지 않은 파일을 오프라인으로 표시하지 않는다. 수동 재검색은 사용자의 명시적 작업으로 처리한다. 위치 이벤트로 전체 컨트롤을 재구성하지 않고 타임라인만 갱신한다. 하드웨어 디코딩 자동 선택과 사용자의 소프트웨어 디코딩 전환은 유지한다.

## 자료와 측정

각 310초인 움직이는 합성 패턴과 AAC 음성: H.264 1080p 24fps(GOP 10초), 30/60fps(GOP 2초), HEVC 4K 10bit 24/60fps(GOP 2초), 15/30fps VFR. 소스 해시는 `.tools/playback-fixtures/manifest.json`에 있다. 실제 사용자 영상의 모든 코덱·자막·가변 비트레이트를 대표하지 않는다. HEVC 10bit 자료는 물리 HDR 출력 검증이 아니다.

각 파일에서 정지 상태 탐색 30회, 드래그 120입력, 반복 키 10회, 1초 워밍업 후 5분 재생을 측정한다. 1280×800 앱 창, 실제 장치 60Hz, 기본 하드웨어 디코딩을 사용한다. OS 파일 캐시를 강제로 비우지 않았으므로 cold-cache 결과로 해석하지 않는다. 일반 성능 비교에서는 자동 추출을 비활성화하고, 백그라운드 작업 연기는 별도 실제 앱 회귀 검사로 확인한다.

Windows는 Build 26300 / Ryzen 7 9700X / RTX 4070 Ti / 드라이버 621.14 / RAM 약 32GiB, `d3d11va-copy`; Mac은 macOS 27.2.1 (26B131) / M4 Mac mini / RAM 16GiB, `videotoolbox`다. 테스트 뷰의 물리 크기·DPR은 Windows 1920×1200·1.5, Mac 2560×1600·2다. Flutter 3.47.9, Dart 3.13.7, media_kit 1.2.6, media_kit_video 2.0.1을 사용했다. 번들 mpv는 Windows `v0.36.0-403-g652a1dd907`, Mac `0.36.0`이다. Windows는 고성능 전원 구성이고 DisplayLink 장치도 존재하므로 이 결과를 모든 디스플레이 출력 경로의 성능으로 일반화하지 않는다.

번들에서 `video-pts`와 `mistimed-frame-count`는 제공되지 않았다. `frame-drop-count`, `decoder-frame-drop-count`, `vo-delayed-frame-count`는 구간 시작과 끝의 차이를 사용한다. 파일 열기·탐색·워밍업 구간의 카운터를 지속 재생 드롭으로 합산하지 않는다. 드래그 표본은 20%→80%의 120입력 궤적이며 2초 GOP 자료의 끝 위치는 키프레임에 가까워질 수 있다. 따라서 한 번의 드래그 종료 시간을 모든 위치의 P95처럼 표현하지 않는다.

원시 결과는 `build/playback-quality/*.json`, 기준 Windows 결과는 `build/playback-quality/baseline/build/playback-quality/*.json`, 실행 로그는 해당 작업 폴더의 `build/verification/`에 저장한다. `tool/summarize-playback.cjs`로 같은 방식으로 집계한다.

기준 앱과 초기 수정본의 6종 × 5분 재생, 각 30회 탐색은 두 OS에서 완료했다. 최종 수정은 탐색 완료 처리와 최종 명령 방식이며, 캐시·지속 재생 설정은 초기 수정본과 같다. 최종본은 다시 6종 × 30회 탐색과 파일별 10초 재생을 검사했다. 따라서 초기 수정본의 5분 결과를 최종 바이너리의 5분 검사로 표시하지 않는다. 아래는 **기준 → 최종본**의 정지 상태 정밀 탐색 P95다. 30개 표본의 최근접 순위 백분위수이며 통계적 유의성을 판정한 실험은 아니다.

기준 앱의 지속 재생 구간에서 네이티브 렌더 드롭은 Windows 6종 모두 0, Mac 1080p60에서 4프레임, 나머지 5종은 0이었다. 디코더 드롭과 캐시 고갈 표본은 모두 0이었다. 이것은 이 조건의 내부 카운터 결과이며 실제 모니터·DisplayLink 경로에서 모든 프레임이 표시됐다는 증명은 아니다. 현재 재현된 주요 결함은 반복 입력의 누락과 탐색 비용이다.

초기 수정본의 6종 × 5분과 최종본의 6종 × 10초에서는 두 OS 모두 렌더/디코더 드롭 및 캐시 고갈 표본이 0이었다. 최종본의 타임라인 목표 표시 P95는 Windows 35.7~37.1ms, Mac 34.7~42.9ms였으며 누락된 UI 표본은 없었다. 이 숫자는 테스트의 입력·펌프 주기를 포함하며 물리 화면의 입력 지연이 아니다.

Mac 1080p60 드래그는 단일 표본이 불안정하여 기준/수정본을 각각 30회 측정했다. 최종본의 중앙값은 133.9 → 50.0ms로 줄었지만 P95는 284.4 → 299.0ms로 조금 높았다. 초기 수정본은 중앙값 253.6ms여서 그대로 채택하지 않았다. 미리보기 완료를 기다리는 방식, 모든 미리보기의 정밀 탐색, 이벤트 상태만 이용한 완료 판단은 이 비교에서 개선을 확인하지 못해 제외했다. 최종본도 긴 꼬리 지연을 제거했다고 주장하지 않는다.

64/32MiB와 128/64MiB의 전방/후방 캐시를 같은 6종에서 비교했다. 큰 캐시는 탐색 지연을 일관되게 줄이지 못해 64/32MiB를 기본으로 선택했다. 디스크 캐시는 사용하지 않는다. H.264 1080p30의 약 30초 자원 표본에서 Windows 앱 CPU 평균은 기준 1.53%, 초기 수정본 1.31%, 최대 GPU 엔진 사용률은 둘 다 4%였다. private working set 최대는 418.4 → 448.0MiB였다. 짧은 표본이므로 CPU 개선을 일반화하지 않는다.

## 최종 회귀와 장시간 검사

정적 검사와 단위/위젯 검사는 두 OS 모두 최종본 119개 통과, 기존 skip 2개다. 초기 수정본에서는 두 OS 모두 같은 검사 및 기존 `app_playback`, `extended_flow`, `privacy_flow`가 통과했다. 최종 `seek_flow`도 두 OS에서 통과했으며 키·마우스, 일시정지, 음량 유지, 되돌리기, 파일 교체, EOF 후 탐색, 3배속, 탐색 직후 일시정지·배속 변경, 자동 스캔 연기를 검사한다.

Windows 외장 SanDisk Extreme 55AE 2TB USB SSD(exFAT)에서는 긴 GOP 영상의 탐색 P95가 333.6 → 200.1ms, 드래그 종료가 300.3 → 183.1ms였다. 반복 키 입력은 30초에서 올바른 60초로 바뀌었다. 기존 외장 4K60의 5분 재생도 드롭·캐시 고갈 없이 통과했다. Mac에는 외장 디스크가 연결되어 있지 않아 해당 조건은 검사하지 않았다.

최종본은 HEVC 4K60 10bit 파일을 Windows 외장 SSD와 Mac 내장 SSD에서 각각 30분 반복 재생했다. 두 장비 모두 실제 EOF 전환 5회, 재생 위치의 지속적인 진행, 마지막 정밀 탐색을 확인했다. 아래 드롭 수는 반복 때 초기화되는 카운터를 구간별로 합산한 값이다. 마지막 카운터만 읽으면 앞선 반복에서 발생한 드롭이 누락된다.

## 다른 플레이어 실측

참조 플레이어도 같은 6종 자료를 순차 재생했다. 앱별 네이티브 렌더러·mpv 버전·하드웨어 경로가 다르므로 순위나 개선 배수로 해석하지 않는다. mpv/IINA는 Lua에서 보낸 정밀 탐색 명령부터 `playback-restart`와 목표 timestamp까지 측정하며 Qt/AppKit 마우스 입력 시간을 포함하지 않는다. Soft Vault 결과는 Flutter 입력 콜백과 폴링을 포함한다.

Windows mpv `v0.42.0-38-gbcde6b93c`(`d3d11va`)의 30회 탐색 P95는 자료 순서대로 34.4 / 116.7 / 33.2 / 64.7 / 33.4 / 97.2ms였다. 파일별 10초 구간에서 렌더·디코더 드롭은 모두 0이었다. Soft Vault가 이 직접 렌더링 경로와 동등한 성능에 도달한 것은 아니다.

Windows VLC 3.0.23은 libVLC의 실제 영상 창에서 같은 파일별 10초 지속 재생을 확인했으며 `lost_pictures` 증가가 모두 0이었다. 정지 상태 탐색에서 `displayed_pictures`가 안정적으로 증가하지 않아 첫 목표 프레임 시간을 얻지 못했다. `set_time` 수락 시간은 기록하되 탐색 완료 시간으로 비교하지 않는다. 최초 실패는 이 측정 코드의 가정 오류였으며 VLC의 재생 실패로 계산하지 않는다.
